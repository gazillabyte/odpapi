# Adapter interoperability contract

This document describes a technical integration contract for independent
ODPAPI adapters. It is not a legal agreement, certification, or guarantee of
compatibility. The Apache-2.0 license applies to the ODPAPI project materials;
it does not require an independently written adapter to be open source.

Adapter authors and providers should agree on the exact protocol version,
routes, fields, status values, authentication method, and error handling used
by their integration. These project materials do not define every provider's
deployment details.

## Compatibility expectations

An adapter should:

1. State which ODPAPI version and operations it implements.
2. Exchange JSON requests and responses over stateless HTTP(S) calls, using the
   authentication mechanism agreed with the provider. Operation arguments may
   be supplied as URL query arguments or, when the adapter documents POST
   support, as members of the JSON `request` object.
3. Preserve identifiers and request sequence information for operations that
   accept request object arrays so object-level results can be correlated with
   request entries. Library-scoped inventory enumeration may assign sequences
   to returned objects because it has no corresponding input object list.
4. Report request-wide errors separately from per-object outcomes.
5. Document how provider objects and libraries map to ODPAPI identifiers and
   fields, including any GUID encoding and scope assumptions.
6. Define behavior for unknown objects, invalid data, duplicate objects,
   unavailable endpoints, retries, and partial success.
7. Avoid exposing credentials, tokens, or sensitive customer data in source,
   logs, public examples, or test fixtures.
8. Test against synthetic fixtures or a provider-authorized test endpoint, not
   production data.

## Shared libodpapi requirement

Adapters must use the shared `libodpapi` public API for standard ODPAPI
responses and objects. This includes the response prolog and epilog, common
result/status text, and the list, inventory, find, move, scan, and add response
helpers where applicable. An adapter must not create adapter-local replacement
JSON code to emulate, duplicate, or subtly reinterpret `libodpapi` behavior.
Provider-specific data belongs in the adapter; protocol structure and standard
field behavior belong in `libodpapi`.

## Contract change control

An adapter must not introduce new response fields, request fields, routes,
status meanings, or other protocol behavior on its own. Any such addition
requires explicit agreement on the provider/version contract first, followed
by the corresponding shared `libodpapi` and contract update. Adapter-specific
metadata must not be presented as standard protocol fields without that
agreement. If extra data fields are needed outside the Query response, they
must be added to the shared `libodpapi` API and documented here before an
adapter uses them; they must not be implemented only in an adapter.

## Adapter-local UUIDs

UUIDs or GUIDs generated by an adapter identify libraries and objects only
within that adapter's namespace. They are stable addressing values for that
adapter's API, not globally portable media identifiers. A client must not use
an UUID from one adapter as the destination or identity when moving a tape
between adapters. Cross-adapter moves require an agreed provider-level
identifier mapping or integration contract.

## Query capability behavior

The Query operation is the capability-discovery entry point. A client must be
able to call the adapter's query endpoint without query arguments or a request
object. The successful response must identify the functions the adapter offers
in `response.functions`, using the provider's established function names. An
adapter may include additional disclosure or configuration information, but it
must not require an object identifier, library identifier, or request body just
to discover its capabilities. Authentication and authorization may still be
required by the deployment.

## Versioned HTTP route

The ODPAPI Version 1 HTTP resource is rooted at `/dpapi-v1`. A request to the
unqualified base URL `/dpapi-v1` is the service entry point and returns the
standard unknown/error response with a hint to use the Query URL. The explicit
`/dpapi-v1/query` (or `/dpapi-v1/query.json`) route is the capability-discovery
request and must return the Query response without requiring query arguments or
a request body. Other Version 1 operations are addressed below the same root,
for example `/dpapi-v1/list`, `/dpapi-v1/find`, and `/dpapi-v1/inventory`.

The versioned root is part of the HTTP contract so a future protocol version
can be introduced under a separate path without changing the meaning of an
existing Version 1 client request.

Inventory is library-scoped. An Inventory request must provide the source
library identifier using the provider-defined `source_library` argument; an
Inventory request without that argument must return the standard missing-
argument result rather than returning an unscoped database listing.

Find is object-scoped. A Find request must provide the object identifier using
the provider-defined `id` argument; a Find request without that argument must
return the standard missing-argument result rather than behaving as an
unscoped inventory request.

On a successful Find request, `response.objects` contains the library GUIDs
that contain the requested object. An unknown object is a successful lookup
with an empty `response.objects` array; it is not an inventory object with
`status: NOTPRESENT`.

The Find `id` value is a literal object identifier. It is matched exactly and
must not be interpreted as a regular expression, shell glob, or `fnmatch`
pattern.

Adapters must document whether a failed provider endpoint produces a complete
request failure or a partial response. If partial objects are returned, the
request-wide result must identify the failure and the adapter must state
whether callers may safely use the returned objects or should retry.

Check status-code meanings against the current helper enums and the provider's
versioned contract. Record discrepancies and resolve version-specific behavior
with the integration partner before claiming interoperability.

## Inventory optional fields

The standard inventory object may include the boolean fields `encrypted` and
`scratch`. `enum ODPAPISTATUS` represents these values: `UNKNOWN` (`-1`) omits
the field, `FALSE` (`0`) emits JSON `false`, and `TRUE` (`1`) emits JSON
`true`. An adapter must not claim a value merely to populate an optional
field. The Linux SCSI changer adapter therefore uses `UNKNOWN` for both fields
because the media-changer inventory does not report encryption or scratch-media
state.

Inventory objects may also include the numeric `slot` field. It is a 1-based
library element address. The helper omits it when the adapter passes `0`.

The standard inventory `move_date` field represents when the media was queued
for movement. It is not confirmation that the tape physically moved in or out
of the library. An adapter that maps provider inbound or outbound dates to
`move_date` must preserve that provider-specific meaning and must not present
the value as a completed-move timestamp.

The standard inventory `next_move` field represents a provider-supplied future
or scheduled movement date. It must be omitted when the provider does not
provide such a date. For IRM reports, `Rtn-date` is retained as `next_move`;
the field is not treated as evidence that the tape has moved.

The List fields `capacity_total`, `moving_in`, `moving_out`, `scratch_total`, and
`scratch_minimum` are unsigned counts. Adapters that do not track those
counts may report zero. For `moving_in`, `moving_out`, and `scratch_total`,
`UINT_MAX` means unknown and causes the shared helper to omit the field. The
same omission sentinel applies to `capacity_total` and `scratch_minimum`.
These fields do not use `ODPAPISTATUS`; that enum is reserved for tri-state
boolean fields such as `encrypted` and `scratch` in inventory objects.

## Independence and project listing

Adapters may be proprietary or open source, subject to their authors' chosen
licenses and their obligations to their own dependencies and providers. Use of
ODPAPI does not imply endorsement by GazillaByte. Authors who want their
adapter listed should follow [ECOSYSTEM.md](ECOSYSTEM.md) and provide public
project details with permission to publish them.
